1. INTRODUCTION                                                 *dbgrid-intro*

dbgrid turns a plain `.sql` file into a notebook: every line starting with
`-- %%` begins a cell. The notebook opens in its own tabpage with the cells
on one side and a results pane on the other. Moving the cursor into a cell
shows that cell's last result from the cache; nothing is re-run.

Notebooks are stored per project (git root of the current directory) and
carry tags, so `:Dbgrid` and `:Dbgrid tags` find them again.

Requires Neovim 0.10+ and `psql` (PostgreSQL) or `sqlite3` (SQLite) on PATH.

==============================================================================
2. SETUP                                                        *dbgrid-setup*

>lua
  require("dbgrid").setup({
    connections = {
      { name = "local", url = "postgres://localhost/app_development" },
      { name = "prod", url = "$PROD_URL", readonly = true, index_check = "confirm" },
      { name = "fizzy", url = "sqlite:storage/development.sqlite3" },
    },
    layout = { results = "left", size = 0.5, tab = true, number = false },
    query = { limit = 500, confirm_writes = true, server_cancel = true },
    format = { on_save = false, formatter = "auto" },
    index_check = { mode = "warn", min_rows = 10000 },
    ai = { agent = "claude" },
    rails = { enabled = true, environments = { "development", "test" } },
  })
<
Connections are also discovered from `DATABASE_URL` (and `DB_URL`,
`POSTGRES_URL`, `PG_URL`) in the environment and in `.env` files of the
project, from `config/database.yml` of a Rails project (as
`rails:development`, `rails:development.cable`, `rails:test`, ...), and
saved interactively with `:Dbgrid connections`. Saved connections are edited
(`<C-e>` in the picker, `:Dbgrid connections edit`), removed (`<C-x>`,
`:Dbgrid connections remove`) or opened as JSON (`:Dbgrid connections file`);
a renamed connection is followed by the open notebooks that used it. Every
edit drops what is cached behind the connection (resolved form, aws
endpoints, bastion, credentials) like `:Dbgrid aws refresh`.

SQLite urls: `sqlite:path/to.db` (relative to the project root),
`sqlite:///abs/path.db`, `~/x.db`, or a bare path ending in .sqlite3 / .db.

Storage: `storage.mode` is "auto" (use `<root>/.dbgrid` when it exists, else
the data directory), "project" or "data". The `.sql` and `.json` of a
notebook are made to be committed; the `.cache.json` (the last
`storage.cache_rows` rows per cell and the parameter values typed in) and
`history.jsonl` hold data and are gitignored in a project store, as is
`recordings/` (the CSV files of `-- @record` cells, marks and the report).

See `lua/dbgrid/config.lua` for every default, including all keymaps.

3. NOTEBOOK FORMAT                                             *dbgrid-format*

>sql
  -- %% [k3x9] overdue invoices
  -- ? invoices unpaid for more than :days days
  -- @param days = 30
  select ... where due_on < now() - make_interval(days => :days)

  -- %% [p2m7] per customer
  -- @depends setup
  select c.email, count(*) from {{overdue-invoices}} o ...
<
`-- %% [id] title`   starts a cell; the id is generated and concealed. Cells
                     are referenced by their title slug, id, or `q<n>`.
`-- ? text`          prompt for the agent (|dbgrid-ai|).
`-- @param n = v`    value of parameter `:n` in this cell (`v` is SQL text).
`-- @depends a, b`   run cells a and b first when their result is stale.
`-- @nolimit`        do not add the automatic LIMIT.
`-- @notx`           do not wrap a multi-statement cell in a transaction.
`-- @conn name`      run this cell on another connection.
`-- @agent name`     send this cell's prompt to another agent.
`-- @dryrun`         run a write with RETURNING * and roll it back.
`-- @every 5s`       re-run the cell on that interval (|dbgrid-live|).
`-- @param n = 3`    default for the `:n` parameter (|dbgrid-params|).
`{{name}}`           inline the named cell as a subquery (|dbgrid-params|).
`:name`              a parameter.

==============================================================================
`-- @record [name]`  append every run to a CSV (|dbgrid-monitor|).
`-- @rate [a, b]`    add `a_per_s` columns: change per second since the
                     previous run (|dbgrid-monitor|).
`-- @alert a > 5`    warn when a row meets a condition (|dbgrid-monitor|).
`-- @metrics [a, b]` no SQL: sample CloudWatch for the cell's connection
                     (|dbgrid-monitor|).

6. RUNNING QUERIES                                                *dbgrid-run*

Each run spawns the client (`psql -f -` or `sqlite3`) with the statements of
the cell. Multi-statement cells run in one transaction unless they contain
BEGIN or `-- @notx`.

LIMIT           read-only statements without a top-level LIMIT/FETCH get
                `LIMIT {query.limit}`; the footer reports when it was hit.
Writes          INSERT/UPDATE/DELETE/MERGE/DDL/DO/CALL ask for confirmation
                (`query.confirm_writes`); UPDATE/DELETE without WHERE get a
                louder prompt. The prompt counts the rows an UPDATE/DELETE
                touches (`query.preview_writes`). `readonly` connections
                reject writes.
Cascades        the prompt for a DELETE lists the tables that lose rows
                through ON DELETE CASCADE (transitively), the ones that get
                SET NULL and the ones whose rows would make it fail. A
                TRUNCATE ... CASCADE lists what else is truncated; without
                CASCADE, which referencing tables would make it fail. All of
                it comes from the schema cache, so refresh it (`\s`) after
                changing constraints.
Dry run         `-- @dryrun` or `query.dry_run`: the write runs with
                RETURNING * inside a transaction that is rolled back, also
                on read-only connections.
Undo                                                           *dbgrid-undo*
                Right before an UPDATE or DELETE with a WHERE runs, the rows
                it touches are read with the same WHERE (the primary key and
                the assigned columns for an UPDATE, every column for a
                DELETE) and kept with the result, up to `query.undo_rows`
                (1000) per statement; the footer says so. `\u` in either
                pane (`:Dbgrid undo`) then writes a cell below with the
                reverse: an INSERT of the deleted rows (OVERRIDING SYSTEM
                VALUE when an identity column is among them) or one
                `UPDATE ... WHERE pk = ...` per row with the old values,
                literals typed by the column. Several statements are
                reversed last first; a cell run on another connection gets a
                `-- @conn` line. Nothing runs until you run that cell, which
                keeps its own rows, so it can be undone in turn. The footer
                says why nothing was kept: no WHERE, no primary key, a view,
                more rows than the cap, or a table missing from the schema
                cache. Generated columns are left out; dry runs keep
                nothing. `query.undo_rows = 0` turns the capture off.
DDL warnings    CREATE/DROP INDEX without CONCURRENTLY on a big table,
                ALTER TABLE (type changes, SET NOT NULL, constraints without
                NOT VALID, volatile defaults), TRUNCATE, VACUUM FULL,
                CLUSTER, REINDEX and a missing `lock_timeout_ms` are listed
                in the confirmation (`query.ddl_warnings`).
Session         `query.session = true` (or `session = true` per connection)
                keeps one psql alive across runs: temp tables and SET carry
                over and the connection handshake is paid once. Cancelling
                ends the session; the next run starts a new one.
Index check     `index_check.mode`: "warn" (default), "confirm" or "off".
                Statements are EXPLAINed first; a Seq Scan on a table with at
                least `index_check.min_rows` rows, or an Index Scan with a
                Filter but no Index Cond, produces a warning with a suggested
                `CREATE INDEX`. SQLite: `SCAN t` in EXPLAIN QUERY PLAN.
                Plans are kept with the result.
Dependencies    `-- @depends a, b` cells run first when their result is
                stale; `run all` follows the dependency order.
Cancel          `\x` sends SIGINT to the client. When the query is still
                running after `query.cancel_grace_ms` (1500), the server is
                asked directly (pg_cancel_backend on the run's own backend,
                found through its unique application_name) and the client is
                killed as a last resort. `query.server_cancel = false` keeps
                the client-only behaviour.
Errors          shown in the results pane and as a diagnostic on the
                offending line of the cell.
Pins            `\P` in the results pane (or `:Dbgrid pin`) keeps the shown
                result in its own small window while the pane follows the
                cursor and new runs; a pin re-renders when its cell re-runs
                (live ticks included) and closes with `q`, a second `\P`, or
                the notebook.

7. PARAMETERS AND REFERENCES                                   *dbgrid-params*

`:name` and `{{name}}` in a cell are placeholders (outside strings, comments
and `::casts`). On run each is replaced by the first of:
  1. the value of a `-- @param name = value` line in the cell,
  2. a value the notebook remembers (earlier prompt, `:Dbgrid param`),
  3. a value you are asked for, which is then remembered.
Values are SQL text: `'2026-01-01'`, `42`, `now()`. The result footer shows
the values used; `\p` lists every parameter with its value and the cells
using it. Substitution happens before the statement is sent, so error lines
still match the cell.

`{{name}}` names a cell (title slug, id or `q<n>`): that cell is inlined as
a parenthesised subquery with comments removed. It must be one read-only
statement; cycles are reported; its own `-- @param` values are kept. The
footer lists what was inlined; completion offers cell names after `{{`.

Secrets ~
                                                              *dbgrid-secrets*
`-- @secret name = spec` is a parameter read from AWS Secrets Manager when
the cell runs, through the cell's connection (one with an `aws` block, same
profile and region). The value is substituted for `:name` as a SQL string
literal and never remembered: it is not written to the notebook, the result
cache or `history.jsonl` (which keep `:name`), and it is masked in results
and error lines. The spec is:
>sql
  -- @secret pw = prod/db                 the secret's `password` key
  -- @secret key = prod/api#api_key       another key of a JSON secret
  -- @secret conn = conninfo:prod/db      host=... port=... dbname=... user=...
                                          password=... sslmode=require, from
                                          an RDS-shaped secret; words after
                                          the id are added (or override):
  -- @secret conn = conninfo:prod/db sslmode=verify-full
  -- @secret pw = scram:prod/db           the SCRAM-SHA-256 verifier of the
                                          password, hashed here
  -- @secret pw = prod/db via other conn  read through another connection
<
The `conninfo` form is what `CREATE SUBSCRIPTION ... CONNECTION :conn` needs.
The `scram:` form is for `ALTER ROLE ... PASSWORD :pw`: the server stores the
verifier as it is, like psql's `\password`, so the password itself is never in
the statement (server log, pg_stat_statements). It takes a printable ASCII
password. `via <connection>` (the rest of the line, names may have spaces)
reads the secret with that connection's profile and region, for a secret that
lives in another account or region than the database the cell runs on.
Statements that cannot run inside a transaction block (CREATE SUBSCRIPTION,
VACUUM, CREATE INDEX CONCURRENTLY, CREATE DATABASE, ALTER SYSTEM) are
detected: a multi-statement cell holding one runs without the per-cell
transaction, and a dry run of it is refused. The server keeps the
connection string in `pg_subscription`, readable by superusers.

8. FORMATTING                                              *dbgrid-formatting*

`\=` (`:Dbgrid format`) reformats the SQL of the cell; the header, prompt and
directive lines are untouched. The formatted text must be the same statement
token for token (keyword case aside) or the cell is left alone with a
warning. Formatting does not mark the cell as edited.

`format.formatter`: "auto" (conform.nvim with a sql formatter, else the first
of `format.order` on PATH — pg_format, sql-formatter, sqlfluff, sqlformat —
else "builtin"), "builtin", "conform", a name from `format.commands`, or
`{ cmd = { ... } }`. Built-in options: `keyword_case` ("keep", "upper",
"lower"), `width`, `indent`. `format.on_save = true` formats every cell on
write.

9. PLANS AND EXPLAIN ANALYZE                                  *dbgrid-explain*

`\e` shows the plan of the first statement; `\E` runs EXPLAIN (ANALYZE,
BUFFERS) inside a rolled-back transaction and adds actual rows and times to
every node. Findings appear above the plan:
  - row estimates 10× off (with `ANALYZE table;` or CREATE STATISTICS hints)
  - sorts / hashes / hash aggregates that spilled to disk (work_mem)
  - scans that discard most of what they read (suggested CREATE INDEX)
  - sequential scans repeated inside a nested loop
  - the node that takes most of the time; temp blocks written
Estimates that are far off are also marked inline. SQLite has no EXPLAIN
ANALYZE; `\E` shows the query plan.

10. PROMPT TO SQL                                                  *dbgrid-ai*

Write `-- ? what you want` in a cell and press <CR> (cell without SQL) or
`\g`. The prompt, the relevant tables of the schema, enum types, the
notebook's parameters and the other cells are sent to the agent. The answer
replaces the SQL under the prompt lines and the cell is marked "generated,
not run". When the cell already has SQL the prompt is an edit request.

The agent is chosen per cell (`-- @agent kimi`), per notebook (`\a`,
`:Dbgrid agent kimi`) or by `ai.agent`. Agents (`ai.agents`) are argv lists;
`{prompt}` and `{output}` are substituted,
`stdin = true` pipes the prompt, `env` adds variables to the agent's
environment (for instance CLAUDE_CONFIG_DIR, to run `claude` with another
account). Defaults exist for `claude`, `kimi`, `codex` and `cursor`; add your
own the same way. In a Rails project the agent is told
about Rails naming conventions.

Asking about a result ~
                                                              *dbgrid-review*
Needs one of the agent CLIs (`claude`, `kimi`, `codex`, `cursor-agent`, or one you add) on
PATH; see |dbgrid-ai| for how agents are configured and picked.

`\a` in the results pane, `\?` on a cell, or `:Dbgrid review [question]`
sends the cell's SQL and its result together to the notebook's agent with
your question (`ai = false` on the connection turns it off), and shows the answer
in a float (`q` closes, `\a` inside asks a follow-up, an empty question
re-opens the last answer). The prompt holds the SQL as it ran, the rows as
displayed (filter and sort respected, at most `ai.max_result_rows`),
command tags, notices, index-check warnings, the error with DETAIL and HINT,
the EXPLAIN output when one was run (else the estimated plan from the index
check), the tables the query reads, and the earlier questions about the
same result. The transcript is kept per cell until the cell is run again;
`\x` cancels a pending question.

11. PLAN ANALYSIS WITH THE AGENT                              *dbgrid-analyze*

`\A` (`:Dbgrid analyze`) runs EXPLAIN (ANALYZE, BUFFERS, SETTINGS, FORMAT
JSON) on the cell inside a rolled back transaction (`ai.analyze.mode =
"estimate"` skips ANALYZE; writes ask first), gathers the tables' columns,
indexes and pg_stat_user_tables counters, applies the `analyze_rules`
(estimate off by `estimate_ratio`, sorts/hashes spilling to disk, the node
with the highest exclusive time, filters discarding most rows) and asks the
agent for: what is slow, why, the fix as SQL, what to verify. The answer
opens in a markdown window: `i` inserts its sql blocks as cells below the
analyzed cell, `y` yanks, `q` closes. It is kept with the result and shown in
the plan view (`\p`), which also renders actual times and buffers.

`\!` explains the cell's last error the same way; `\l` shows that error
as it is (message, position, detail, hint, context) in a float
where `y` yanks it. `\g` on a cell whose last run failed also hands the
agent that error. `\i` needs the hypopg
extension: the suggested index is created hypothetically in the same
session, the statement is re-explained and the cost before and after shown.

`ai.redact_literals` replaces literals before anything leaves the machine;
`ai = false` on a connection disables the agent for it; `ai.investigate`
gives the agent a read-only `dbgrid-query` shell helper on the connection.

12. TEMPLATES                                               *dbgrid-templates*

`:Dbgrid new --template diagnostics`, `blue-green`, `logical-replication`
and `create-replication` copy a bundled notebook into the project. Diagnostics: active queries,
blocking tree, idle in transaction, long transactions, top statements
(pg_stat_statements), seq scans, dead tuples, unused and redundant indexes,
cache hit ratio, sizes, connections, wraparound, temp files, replica lag,
replication, settings, extensions, locks on a table, cancel a backend.
Blue-green: slot lag, sender and subscription state, writes in flight, rows
written, application sessions, long transactions, tables without replica
identity, row counts and sequences on both sides, green accepts writes; every
cell is read-only. Logical-replication: a publication / subscription
migration (RDS PostgreSQL to Aurora, or any two servers) seen from both
sides: slot lag and retained WAL, initial sync progress, copies running,
workers, subscription errors, sessions, counters with their rates and
CloudWatch for the source and the target (recorded, see |dbgrid-monitor|),
settings, publications, tables not published or without replica identity,
row counts and sequences on both sides, writes in flight; every cell is
read-only. Create-replication: the steps of that migration in order:
preflight on both sides, truncate the target, drop the secondary indexes for
the copy (definitions saved in an `ops` table), CREATE SUBSCRIPTION with the
connection string from a secret (|dbgrid-secrets|), pause and resume, then
rebuild and check the indexes (against the saved definitions and, with
`:Dbgrid diff`, against the source), analyze, reset and check the sequences,
a lag probe, a stream rate test and a rollback (drop, or detach first on a
restored copy of the target); the subscription and publication names are
the `:sub` and `:pub` parameters. Its write cells are
real writes. Cells with `-- @conn blue|green` (`source|target`) are bound to
the connections you pick, and so is a placeholder after `via` on a
`-- @secret` line. `templates.dir` adds your own (header lines
`-- template-name:`, `-- template-tags:`, `-- template-description:`,
`-- template-connections:`; `source = prod/writer` offers that connection
first on creation).

13. LIVE CELLS                                                  *dbgrid-live*

`-- @every 5s` (`500ms`, `2m`) makes a read-only cell live: running it once
keeps it re-running until `\x`, an edit, an error or closing the notebook.
Ticks are skipped while one is in flight; changed values are highlighted
(|hl-DbgridChanged|); `\h` draws a sparkline of the numeric column under the
cursor over the last `live.history` ticks; `live.max_cells` caps the loops
per notebook. Live results are written to the cache when the loop stops.

==============================================================================
14. DIFFS, HISTORY, EXPORT                                       *dbgrid-diff*

`\d` diffs the current result against the previous run of the cell, matched
by the table's primary key (or an `id` column, or whole rows).
`:Dbgrid diff {connection}` runs the cell on another connection and diffs.
`:Dbgrid schema diff a b` and `:Dbgrid settings diff a b` open a scratch
buffer (`]c` / `[c` jump between tables, `q` closes).
`:Dbgrid live all` starts every `-- @every` cell that is not live yet,
past `live.max_cells`; `live all pin` also pins the recorded ones.

MONITORING A RUN                                              *dbgrid-monitor*

`-- @record` appends the first result set of every run of the cell (live
tick or not) to `<store>/recordings/<notebook>/<cell title>.csv`, the time
of the run first (`ts`); `-- @record lag` names the file. A run without rows
leaves a line with only the time, a failed run nothing; when the columns
change the old file is renamed aside. `:Dbgrid recordings` lists the files.

`-- @rate a, b` adds an `a_per_s` column next to each named column: the
change since the previous run divided by the seconds between the two (for
counters that only grow). Bare `-- @rate`: every numeric column. The first
run and a counter that went down give NULL. Rows are matched by the first
column that gets no rate.

`-- @alert col > 5, other = text` raises an alert when any row meets any
condition (`>` `>=` `<` `<=` `=` `!=`; NULL never matches): a warning when
it starts, a note when it clears, a marker on the cell meanwhile, and for a
recorded cell a line in the report's timeline.

`-- @metrics [names]` makes a cell without SQL that samples CloudWatch for
its connection (an AWS connection with `cluster` or `instance`): the newest
datapoint of each metric as one row, bytes in MiB and latencies in ms. One
datapoint a minute, so `-- @every` is at least 60s. Needs
`cloudwatch:GetMetricData`.

`:Dbgrid mark [text]` notes a moment (`recordings/<notebook>/marks.csv`).
`:Dbgrid recordings report [file]` writes markdown: the timeline of marks
and alerts, then per recording min / avg / max / last and a sparkline of
every numeric column, the states of text columns, and averages per phase
between marks.

Every statement is appended to `<store>/history.jsonl` as it ran, with
parameter values substituted (`history.enabled`, `history.max_entries`;
gitignored in a project store); `\H` / `:Dbgrid history` inserts an entry
as a new cell, <C-y> yanks it. `:Dbgrid export md [path]` writes the notebook as
markdown with SQL, results and analyses.

15. AWS RDS AND TUNNELS                                           *dbgrid-aws*

>lua
  { name = "prod", aws = { profile = "prod", region = "ap-southeast-1",
      cluster = "app-prod", bastion = "i-0123456789abcdef0",
      secret = "prod/db",
      login_cmd = { "company-aws-login", "--profile", "{profile}" } } }
<
The entry appears as `prod/writer` and `prod/reader` (readers are
read-only; plain RDS gets one reader per replica). On the first run the
endpoints are resolved with the aws CLI and cached (`aws.endpoint_ttl_seconds`),
an SSM port forward to the bastion is started and kept for the session
(before every run it is probed with a PostgreSQL handshake and replaced
when the session behind it has died; a run that still cannot reach the
server rebuilds the tunnel and retries once), the password comes from
Secrets Manager (or `auth = "iam"`) and goes to psql through the
environment. The database is `aws.database`, else the secret's
`dbname` (or `db`), else the cluster's initial database; otherwise you are
asked once and the answer is saved on the connection. The URL keeps the real host with `hostaddr=127.0.0.1`
so `ssl = "verify-full"` with `sslrootcert` and ~/.pgpass work. Expired
credentials run `aws.login_cmd` (`{profile}` substituted) in a terminal
split and retry. Without `bastion` the connection is direct; `aws.document`
and `aws.parameters` cover custom SSM documents.

`bastion` is an instance id, the Name tag of an instance or "auto". Without
an instance (Fargate), an ECS Exec target works too:
`ecs:<cluster>_<task id>_<runtime id>`, passed to SSM as is. A name
or "auto" is looked up among the SSM-managed instances when the tunnel is
first started (`ssm describe-instance-information` + `ec2 describe-instances`)
and cached with the endpoints; a tunnel that fails to start, and `aws
refresh`, drop the cached id so a replaced jumpbox is found again. "auto"
takes the online instance whose name contains one of `aws.bastion_names`
(`{ "bastion", "jump" }`), preferring the database's VPC. Without permission
to list SSM instances the running EC2 instances are offered by name; when
neither listing works the instance id is asked for, and the prompt says why.

A database in another account reached through a VPC endpoint has nothing to
describe: leave out `cluster` / `instance` and give `secret` (its `hostWrite`,
`hostRead`, `port` and `db` are used) or `host` / `read_host` / `port`. The
tunnel, credentials, writer/reader entries and health checks work as usual;
`aws status`, `aws events` and `aws bluegreen` need a describable database.

`:Dbgrid aws add` builds an entry interactively (the bastion is picked from
the SSM-managed instances; one clear jumpbox is taken without asking; the
last entry of the cluster list reaches a database by host name);
`aws login`, `aws refresh`,
`aws tunnels`, `aws status` (status, version, maintenance, five CloudWatch
metrics), `aws events` (last day), `aws bluegreen` (deployments and
switchover status). `:checkhealth dbgrid` covers the CLI, the Session
Manager plugin, credentials and tunnels.

Generic tunnels: `tunnel = { kind = "ssh", host = "bastion" }` (remote
defaults to the URL's host:port) or `tunnel = { kind = "cmd", cmd = { ...,
"{port}" } }`; `local_port` fixes the local port.

16. SCHEMA AND COMPLETION                                      *dbgrid-schema*

The schema (tables, columns, keys, indexes, enums) is fetched once per
connection, cached on disk and refreshed after `schema.ttl_seconds` or `\s`.

`K`   describes the table or column under the cursor (columns, defaults,
      foreign keys with their ON DELETE rule, indexes, and the tables that
      reference it) in a float.
`\k`  opens the foreign-key tree of the table (`:Dbgrid relations [table]`,
      |dbgrid-relations|).
`\S`  picks a table (preview = the same description) and inserts its name.
`\b`  shows the schema document in the results pane: one fold per table
      with columns, indexes and foreign keys. Tables used by the current
      cell start open, the rest closed; `/` searches, `\f` filters by
      table name; the document stays while moving between cells and
      gives way to the result when a cell is run.

Completion: blink.cmp provider `{ name = "dbgrid", module =
"dbgrid.completion.blink" }`; nvim-cmp `require("cmp").register_source(
"dbgrid", require("dbgrid.completion.cmp").new())`; omnifunc by default.
Items: columns of the tables in the statement first, alias-qualified columns
after `alias.`, tables, schemas, keywords and functions of the connection's
dialect, cell names and parameters after `{{`, parameters after `:`. In a
comparison string on an enum column (`status = '…`, `in ('…`) only the
enum's values are offered.

                                                            *dbgrid-relations*
`\k` or `:Dbgrid relations [table]` opens the foreign-key tree of a table:
what it references, what references it (`schema.relations_depth` hops each
way, cycles marked), and what a DELETE on it would reach. On `u.email` the
table is whatever `u` aliases in the current cell.

PostgreSQL (`psql`) and SQLite (`sqlite3`) are built in.
`require("dbgrid").register_adapter(adapter)` adds another database. See

`cancel(job, conn)`, `keywords`, `functions`, `dialect`, `analyze`).

18. ACTING ON A RESULT                                       *dbgrid-actions*

All of these work on the row and column under the cursor in the results pane.

Follow        `gf` follows the foreign key of the value: on `user_id = 42` the
              pane shows `SELECT * FROM users WHERE id = 42`; on a primary
              key it shows the rows that reference it (a picker when several
              tables do). Keys from the schema cache come first; without one,
              `user_id` → `users.id` and `users.id` ← `*.user_id` are
              guessed by name. The lookup belongs to no cell: `gf` again
              follows further, `gF` keeps it as a cell, `]c` or a run brings
              the pane back. `gF` on an ordinary result follows into a new
              cell.
Next page     `\m` (`:Dbgrid more`) re-runs a statement whose LIMIT dbgrid
              added, with an OFFSET, and appends the rows; the footer counts
              the pages. Without ORDER BY pages may overlap. Every row stays
              in memory; the disk cache keeps `storage.cache_rows` of them.
Edit          `\e` asks for a SQL expression (prefilled with the value as a
              literal) and writes `UPDATE t SET col = … WHERE pk = …` as a
              new cell below the current one. The table's primary key has
              to be in the result. Nothing runs until you run the cell.
Undo          `\u` (`:Dbgrid undo`) writes the statements that put the rows
              of the cell's last UPDATE / DELETE back as they were right
              before it ran, as a new cell below. See |dbgrid-undo|.
Backends      `\x` on a row with a pid column (`pid`, `blocking_pid`,
              `blocked_pid`, or the column under the cursor when its name
              ends in `pid`) offers pg_cancel_backend / pg_terminate_backend
              and re-runs the cell. PostgreSQL only.
Columns       `\c` hides the column under the cursor, `\C` shows hidden
              ones again (a picker; `:Dbgrid columns show all`). Remembered
              per cell; `\ya` yanks the visible columns.
Chart         `\g` draws the numeric column under the cursor (else the
              first numeric one) by the first text column as horizontal
              bars; sort and filter apply. `:Dbgrid chart value by label`
              names the columns; `-- @chart value by label` in a cell shows
              the chart whenever the cell runs. `results.chart_width` fixes
              the bar width. Groups: |hl-DbgridChartBar|,
              `DbgridChartBarNeg`, `DbgridChartLabel`.
Import        `:Dbgrid import {file} [table]` reads the header of a CSV /
              TSV (delimiter detected), checks the columns against the
              table, confirms, then loads it: psql's `\copy` on PostgreSQL
              (the file is read locally), `.import` on SQLite. Without a
              table a picker lists them, plus a new table created from the
              header (text columns). Afterwards the table is shown in the
              results pane.
